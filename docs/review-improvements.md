# 프로젝트 검토 후 개선 사항

## 토큰 변경의 시각적 정확성

Inspector와 Figma 검토 창이 목록 순서에 따라 같은 색을 표시하던 문제를 수정했습니다. 공통 `TokenSwatch`가 `@aster-ui/tokens/json/coral`과 `json/ocean`의 빌드 산출물에서 별칭을 해석합니다. 해석할 수 없으면 임의의 색 대신 `Color unavailable`을 표시합니다.

작업 영역의 `Tokens`에서 선택한 테마의 해석된 색상 값을 확인할 수 있습니다. 그 아래의 `Pending change preview`는 Figma 검토 대상 테마를 기준으로 실제 공용 Button, 포커스 테두리, 강조 글자의 변경 전후를 비교합니다. 변경 적용이나 추가 승인은 실행하지 않습니다.

과거 토큰에는 낮은 대비의 색상도 포함될 수 있습니다. 비교 표본은 조작 불가능한 시각 참고 자료로 표시하고 접근성 트리에서 제외합니다. 각 표본의 Before/After, 토큰 이름, 별칭과 실제 색상 값은 접근 가능한 텍스트로 별도 제공합니다. 실제 조작 UI의 접근성 검사는 그대로 유지합니다.

## 저장소 접근 실패와 요청 취소

- `localStorage` 객체를 얻는 단계부터 예외를 처리합니다. 접근이 차단된 환경에서는 탐색을 유지하고 저장 불가 안내를 표시합니다. 메모리에 저장한 결과를 영구 저장 성공으로 표시하지 않습니다.
- 이미 취소된 요청은 기존 완료 기록을 재사용하기 전부터 거절합니다. 지연이 끝난 뒤에도 실제 저장 직전에 취소 여부를 확인합니다.
- 완료 또는 취소 시 이벤트 리스너를 제거합니다. 취소된 제공자의 늦은 성공과 실패 응답은 현재 릴리스 상태를 변경하지 못합니다.
- 저장소 getter의 `SecurityError`, 지연 완료 직후 취소, 취소된 요청의 재사용, 늦은 응답을 회귀 테스트로 검증합니다.

## 브라우저 성능 측정

`pnpm perf:check`는 기존 프로덕션 자산 용량 예산을 검사합니다. `pnpm test:visual`은 화면 검증과 함께 초기 렌더링 성능을 측정합니다. `pnpm verify`가 두 검사를 모두 실행하며, 어느 쪽이든 실패하거나 현재 소스와 근거가 다르면 릴리스 품질 검사를 통과하지 못합니다.

| 조건 | 값 |
| --- | --- |
| 대상 | 로컬 프로덕션 미리보기의 초기 화면 |
| 화면 | 1440 × 1024, 배율 1 |
| 브라우저 | 로컬 Google Chrome, CI Playwright Chromium |
| 실행 | 새 브라우저 컨텍스트 3개, HTTP 캐시 비활성화 |
| CPU | DevTools Protocol 기준 4배 감속 |
| 네트워크 | 다운로드 10 Mbps, 업로드 5 Mbps, 지연 40 ms |
| 관찰 | 글꼴과 이미지 로드 완료 후 1초까지, 사용자 입력 없음 |
| FCP 예산 | 세 실행의 중앙값 3,000 ms 이하 |
| LCP 예산 | 세 실행의 중앙값 4,000 ms 이하 |
| CLS 예산 | 세 실행의 최대 세션 값 0.1 이하 |

`PerformanceObserver`가 지표를 제공하지 않거나 FCP/LCP가 누락되면 검사를 실패시킵니다. CLS는 최근 입력에 따른 이동을 제외하고, 이동 간격이 1초 미만이며 길이가 5초 미만인 세션의 최댓값을 계산합니다. 계산 기준은 [Chrome 팀의 CLS 설명](https://web.dev/articles/cls)을 따릅니다. CPU 감속은 [Chrome DevTools Protocol](https://chromedevtools.github.io/devtools-protocol/tot/Emulation/#method-setCPUThrottlingRate)을 사용합니다.

원시 표본, 실행 조건, 브라우저 버전, 플랫폼과 결과는 `reports/visual-regression.json`의 `browserPerformance`에 기록합니다. 요약은 Studio Quality와 자동 생성 검증 보고서에 반영합니다.

이 예산은 프로젝트의 실험실 회귀 기준입니다. CPU 감속은 호스트 성능에 영향을 받으므로 다른 장비의 수치를 직접 비교하지 않습니다. 실제 사용자 75백분위, 배포 서버 지연, 사용자 세션 전체의 CLS, INP를 측정한 결과로 해석하지 않습니다.

## 검증 방법

Studio 단위 및 상호작용 검사는 `pnpm --filter @aster-ui/studio test`로 실행합니다. axe 검사는 초기 화면, 토큰 비교, Figma 검토, 릴리스 대화상자로 분리해 전역 제한 시간을 늘리지 않고 각 상태를 독립적으로 검증합니다. Studio 테스트 파일은 순차 실행해 React와 axe를 여러 워커가 동시에 로드할 때의 메모리 부담을 줄입니다.

단위 검사에서 대화상자는 활성 대화상자만 검사하고 기본 작업 영역은 별도로 검사합니다. 실제 브라우저의 axe 검사는 계속 문서 전체를 대상으로 실행합니다.

브라우저 검사는 견본의 계산된 색상과 실제 Button 배경 및 포커스 색상, 테마 변경 시 검토 범위 유지, 모바일 넘침, 저장소 차단 시 탐색을 확인합니다. 이 검사를 확장하면서 발견한 토큰 출력 형식 설명의 낮은 대비도 글자색을 진하게 바꿔 수정했습니다. 시각 기준 이미지는 기존 플랫폼별 검토 정책을 유지합니다.

## 추가 디자인·구조 검토 반영

- 검토, 리허설, 검증 상세, 모바일 탐색을 하나의 overlay 상태로 관리한다. 열린 모달에서 검색 단축키가 배경으로 포커스를 옮기지 못하게 하고 배경을 inert 처리했다.
- API manifest의 기본값은 등록된 컴포넌트의 props 매개변수에서만 추출한다. 보조 함수나 함수 본문의 구조 분해는 제외하며 prop 별칭을 지원한다. 지원하지 않는 선언은 조용히 추측하지 않고 오류로 알린다.
- View details는 검증 상세 대화상자를 연다. 검증별 명령, 출처, 브라우저 시나리오, lab 측정값을 확인하고 JSON 근거를 내려받을 수 있다. 과거 또는 실패한 브라우저 보고서는 현재 성공 근거와 구분한다.
- 상단의 중복 탐색을 제거했다. 중앙은 컴포넌트별 Preview/API/Tokens/Quality, 오른쪽은 Props/Changes/Checks 요약이다. 작은 보조 글씨를 공통 크기로 조정하고 상세 보기 버튼 스타일을 통일했다.
- component, tab, theme, platform 쿼리로 화면을 직접 열 수 있다. 새로고침, 뒤로가기와 앞으로가기를 지원하며 잘못된 값은 안전한 기본값으로 해석한다.
- 전체 verify는 커버리지 실행에서 단위 테스트를 함께 검증하고 스크립트 테스트는 별도로 실행한다. Studio 소스 테스트는 의존 패키지만 빌드한다. tokens 산출물 검사, 시각 테스트용 fixture 빌드, 최종 검증 근거를 담는 빌드는 유지했다.

검증 실행 계획에서도 Studio 테스트에 필요한 작업이 자체 빌드를 포함한 5개에서 의존 패키지 빌드 3개와 테스트 1개로 줄었음을 확인했다. 전체 verify의 6개 workspace 테스트는 커버리지 모드로 한 번씩 실행한다. 실행 시간은 다른 작업의 부하에 영향을 받아 고정된 단축 수치를 주장하지 않는다.

최종 검증 근거를 번들에 넣은 뒤에는 `pnpm perf:final`로 자산 예산을 다시 검사한다. 결과는 `reports/final-assets.json`에 별도로 기록해 근거 생성의 순환 의존성을 피하며, 최종 검증 문서의 자산 크기는 이 보고서를 사용한다.
