# Aster UI 디자인 시스템 플랫폼 케이스 스터디

## 한 줄 요약

의료미용 제품군을 가정한 개인 PoC로, Figma 토큰 변경을 React 공개 계약과 저장소의 세 검증용 앱에 대조하고 사람 검토와 릴리스 리허설까지 연결했습니다.

구현의 출발점은 다음 질문이었습니다.

> 디자인 변경을 여러 플랫폼과 제품에 전달할 때, 개발자와 디자이너가 변경 근거와 위험을 같은 화면에서 확인하고 배포 전 판단을 내릴 수 있는가?

## 범위와 제약

- 제품 문제 정의, 정보 구조, 운영 도구 UI, 반응형 구현을 직접 담당했습니다.
- TypeScript, React, Turborepo로 패키지 구조와 공용 API를 설계했습니다.
- W3C DTCG 토큰, Figma Variables 읽기 어댑터, Claude Code 제안 검증, CI와 릴리스 자동화를 구현했습니다.
- 실제 회사 코드, 사용자 데이터, 조직의 Figma 파일은 사용하지 않았습니다.
- Clinic과 Backoffice는 스캐너와 코드 변환 도구를 검증하기 위한 작은 소비 예제입니다. 실제 운영 제품이나 조직 도입 성과로 취급하지 않습니다.

## 결정 기록

### 1. Figma 변경은 자동 반영하지 않고 읽기 전용 검토로 제한했다

**제약**

토큰 자동 동기화는 빠르지만 잘못된 컬렉션, 모드 또는 별칭이 여러 플랫폼에 동시에 퍼질 수 있습니다. 공개 PoC에서는 실제 조직 파일의 권한과 변경 이력도 사용할 수 없습니다.

**검토한 대안**

- Figma 플러그인이 토큰 파일을 직접 수정하고 PR을 생성하는 방식
- 디자이너가 값을 문서에 옮기고 개발자가 수동으로 반영하는 방식
- REST 응답을 정규화해 변경만 보여 주고 사람이 승인하는 방식

**선택과 이유**

세 번째 방식을 택했습니다. Variables REST 응답에서 컬렉션, 모드와 별칭 대상을 먼저 확인하고, DTCG 경로에 존재하는 변경만 검토 화면에 표시합니다. CI에서는 네트워크와 계정 권한에 의존하지 않도록 같은 스키마의 비식별 픽스처를 재생합니다.

**결과와 남은 부채**

별칭이 없거나 대상 경로가 사라진 경우 결과 생성을 중단하고, 검증을 통과한 변경도 사람이 검토한 뒤에만 기록합니다. 실제 Figma 쓰기와 플러그인 배포는 구현하지 않았으므로, 라이브 환경에서는 권한 범위, 속도 제한, 충돌 복구를 추가로 설계해야 합니다.

### 2. 공개 API는 컴포넌트 계약과 TypeScript 공개 export 전체를 함께 비교한다

**제약**

문자열로 추출한 prop 목록만 비교하면 패키지 진입점에서 타입이나 컴포넌트 export가 사라지는 변화를 놓칠 수 있습니다. 반대로 전체 소스 diff를 하위 호환성 판정으로 사용하면 내부 구현 변경까지 차단합니다.

**검토한 대안**

- 생성된 prop 문자열과 수동 메타데이터만 비교
- 빌드된 선언 파일 전체를 텍스트 스냅샷으로 비교
- 컴포넌트 계약 검사와 TypeScript 타입 체커 기반 공개 export 검사를 분리

**선택과 이유**

세 번째 방식을 택했습니다. 레지스트리와 AST 생성기는 6개 컴포넌트의 공개 prop 38개, 기본값, ref와 DOM 속성 계약을 확인합니다. 별도 타입 체커는 `@aster-ui/react` 진입점의 공개 값과 타입 export 23개를 정규화해 승인된 기준과 비교합니다. 새 export와 선택적 prop은 추가 항목으로 기록하고, 제거나 서명 변경은 릴리스를 차단합니다.

**결과와 남은 부채**

prop 목록 밖의 공개 타입과 컴포넌트 export까지 변경 감지 범위를 넓혔습니다. 다만 TypeScript 선언 비교만으로 CSS의 시각적 의미나 런타임 동작을 증명할 수는 없습니다. CSS는 실제 브라우저 시각 회귀가, 키보드와 ARIA 및 이벤트는 상호작용 테스트가 맡습니다. 이 조합도 모든 소비 코드의 호환성을 보장하지는 않습니다.

### 3. 릴리스 판단은 빠른 검사보다 근거의 일치 여부를 우선했다

**제약**

단위 테스트 통과만으로 디자인 시스템을 배포하면 API, 접근성, 스타일, 번들 크기와 공급망 변화가 서로 다른 시점의 결과로 섞일 수 있습니다. 모든 검사를 순차 실행하면 피드백 시간이 길어집니다.

**검토한 대안**

- 단위 테스트와 빌드만 통과하면 배포
- 각 검사를 독립 실행하고 최신 결과라고 가정
- 선행 빌드 뒤 독립 검사를 병렬 실행하고, 소스 리비전과 산출물 해시가 일치한 결과만 승인

**선택과 이유**

세 번째 방식을 택했습니다. API, Figma, AI, 접근성, 시각 회귀, 성능, 보안과 공급망 검사를 나눠 실행하되 각 보고서에 소스 리비전, Git 커밋, 실행 ID와 산출물 해시를 남깁니다. Studio의 릴리스 리허설은 다섯 품질 근거가 현재 빌드와 일치할 때만 활성화됩니다.

**결과와 트레이드오프**

검증한 소스와 화면에 표시한 근거, Pages에 배포한 결과의 관계를 추적할 수 있게 됐습니다. 실제 브라우저 검사와 플랫폼별 기준 이미지를 포함해 CI 시간이 길어졌고, Linux 기준 이미지는 자동 갱신 대신 사람이 검토하는 수동 워크플로로 관리합니다.

### 4. `13/13`을 도입률이 아니라 저장소 표본 커버리지로 한정했다

**제약**

이 저장소에는 실제 조직의 팀 수, 전체 코드베이스, 배포 버전이나 사용량 데이터가 없습니다. 임의로 전체 JSX를 분모로 삼으면 지역 컴포넌트와 문자열까지 섞여 수치의 의미가 흔들립니다.

**검토한 대안**

- 저장소 전체에서 디자인 시스템처럼 보이는 이름을 정규식으로 집계
- 각 소비 앱이 검사 대상을 선언하고 실제 import와 JSX 사용만 AST로 확인
- 표본 수치를 실제 조직 도입률처럼 표시

**선택과 이유**

두 번째 방식을 택했습니다. 표본 수치를 실제 조직 도입률처럼 표시하는 방식은 근거가 없어 제외했습니다. Studio와 두 소비 예제가 `design-system-consumer.json`에 검사 대상을 직접 선언합니다. 분석기는 별칭과 네임스페이스 import를 인식하고 문자열, 주석과 같은 이름의 지역 컴포넌트를 제외합니다.

**결과와 남은 부채**

선언 표본 13개가 실제 JSX에서 사용되고 지원 중단 예정 API 사용은 0건입니다. 이는 스캐너가 세 작은 예제에서 동작한다는 근거일 뿐 실제 조직 도입률이나 제품 성과가 아닙니다. 조직 지표로 확장하려면 소비 팀, 패키지 버전, 기간과 제외 기준을 저장소 밖의 데이터 소스로 수집해야 합니다.

### 5. 구성 요소의 수보다 변경 전달 구조를 먼저 검증했다

**제약**

짧은 PoC에서 컴포넌트와 토큰 수를 늘리면 표면적은 넓어지지만 각 항목의 API, 접근성, 문서와 마이그레이션 계약이 얕아질 수 있습니다.

**선택과 이유**

색상, 간격, 모서리 반경을 다루는 DTCG 핵심 경로 31개와 React 컴포넌트 6개로 범위를 고정했습니다. 대신 토큰 변경, 공개 API, 소비 표본, AI 제안, 품질 근거와 릴리스 판단이 하나의 흐름으로 이어지는지 확인했습니다.

**다음 단계**

Typography, elevation, motion, density는 플랫폼별 의미와 접근성 완료 조건을 먼저 정의한 뒤 추가합니다. 이후 실제 소비 요구가 두 곳 이상에서 확인된 컴포넌트부터 확장합니다. 순서와 완료 조건은 [디자인 시스템 확장 로드맵](roadmap.md)에 정리했습니다.

## 검증 결과

| 영역 | 저장소에서 확인할 수 있는 근거 |
| --- | --- |
| 공용 React | 컴포넌트 6개, 공개 prop 계약 38개, TypeScript 공개 export 23개 |
| 디자인 토큰 | 색상, 간격, 모서리 반경의 DTCG 핵심 경로 31개, Coral과 Ocean, CSS와 Swift와 Compose 산출물 |
| Figma | REST 스키마 어댑터, 별칭 변경 테스트 픽스처 3개, 읽기 전용 사람 검토 |
| 소비 표본 | 검증용 앱 3개가 선언한 대상 13/13개 사용, 지원 중단 예정 API 사용 0건. 조직 도입률이 아님 |
| 마이그레이션 | `PrimaryButton`을 `Button`으로 바꾸는 TypeScript AST 코드 변환 테스트 픽스처 |
| AI | Claude Code 구조화 제안, 결정론적 검증, 변조와 경로 이탈 차단, 제한 시간, 별도 승인 기록 |
| 품질 | 단위와 상호작용, axe, 실제 Chrome 시각 회귀, 확대, 모바일, forced-colors, 성능과 보안 검증 |
| 운영 | release-please, 변경 불가능한 Action SHA와 이미지 해시, 비루트 읽기 전용 컨테이너, 전체 검증 뒤 Pages 배포 |

실행 시점과 소스 리비전이 포함된 최신 수치는 [`reports/verification.md`](../reports/verification.md)와 각 JSON 근거에서 확인할 수 있습니다.

## 구현하지 않은 범위

- Figma 라이브 API에는 Figma 플랜, 사용자 라이선스, 파일 권한과 `file_variables:read` 범위가 필요합니다.
- Swift와 Compose 산출물은 공유 토큰입니다. 네이티브 컴포넌트를 구현했다고 표현하지 않습니다.
- npm 레지스트리 배포와 실제 조직 도입 지표는 범위 밖입니다. `Run rehearsal`은 외부 상태를 바꾸지 않습니다.
- Claude Code 라이브 제안에는 해당 환경의 로그인이 필요합니다. CI는 같은 계약을 오프라인 픽스처로 검증합니다.
- VoiceOver와 NVDA의 수동 사용성 검증, 실제 Kubernetes 클러스터 스모크 테스트는 수행하지 않았습니다.

## 5분 검토 순서

1. Studio에서 6개 컴포넌트를 선택해 미리보기와 생성 API가 함께 바뀌는지 확인합니다.
2. `Tokens`에서 실제 Button의 변경 전후를 비교한 뒤, `Review changes`에서 Figma 별칭 변경과 Web, iOS, Android 토큰 영향을 확인하고 사람 검토를 기록합니다.
3. `Quality`에서 소스 리비전과 각 근거 해시, 초기 로드 성능 측정 결과를 확인합니다.
4. 검토와 품질 근거가 준비된 상태에서 외부 배포 없는 릴리스 리허설을 실행합니다.
5. 코드에서는 `packages/figma-bridge`, `scripts/lib/public-api-surface.mjs`, `scripts/generate-ai-proposal.mjs`, `scripts/scan-consumer-coverage.mjs`, `.github/workflows/ci.yml` 순서로 확인합니다.

## 재현

```bash
pnpm install --frozen-lockfile
pnpm verify
```

Figma와 AI 테스트 픽스처만 빠르게 확인하려면 다음을 실행합니다.

```bash
pnpm figma:check
pnpm ai:check
```
