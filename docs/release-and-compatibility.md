# 릴리스와 하위 호환

## 버전 계약

루트의 버전은 Studio, 패키지 3개, 토큰 상수, 컴포넌트 매니페스트, release-please 매니페스트, 변경 이력, Kubernetes 버전 메타데이터에서 동일해야 합니다. 실제 Kubernetes 이미지는 별도 렌더러가 `repository@sha256:<digest>` 형식만 허용합니다. `pnpm release:check`는 값이 하나라도 다르면 실패합니다.

release-please는 저장소 루트 하나를 릴리스 대상으로 관리합니다. 루트의 package.json, CHANGELOG.md와 릴리스 매니페스트는 기본 node 전략으로 갱신하며, Studio와 패키지 버전, 토큰 상수, 컴포넌트 매니페스트, Kubernetes의 두 버전 라벨, 생성 API 문서의 버전은 `extra-files`로 함께 갱신합니다. TypeScript, YAML과 Markdown의 갱신 대상 줄에는 `x-release-please-version` 표시를 둡니다. API 호환성 기준 파일은 과거 버전의 계약이므로 자동으로 올리지 않습니다.

빌드 후 검증은 병렬 검사를 시작하기 전에 `pnpm ai:fixture`로 현재 매니페스트에 맞는 오프라인 AI 보고서를 다시 만듭니다. 다음 버전에서 달라지는 manifest와 prompt 해시도 이 단계에서 갱신됩니다. 기존 제안 검사는 여전히 오래되거나 변조된 보고서를 거부하며, 라이브 제안과 사람 승인 기록은 이 준비 단계의 대상이 아닙니다.

스크립트 회귀 검사는 이 설정으로 다음 버전의 변경을 임시 디렉터리에 재현한 뒤 릴리스 계약, 생성 문서와 AI 제안부터 승인까지의 검사를 실행합니다. 이전 AI 보고서는 준비 단계 전에 거부되어야 하고, Kubernetes 라벨 하나만 갱신되거나 패키지별 독립 버전 매니페스트로 돌아가면 실패합니다.

## API 호환성

- 패치: DOM 의미와 사용자 동작을 유지하는 오류 수정
- 마이너: 선택적 prop, 토큰, variant 추가
- 메이저: prop 제거, 필수 prop 추가, 타입이나 상호작용 의미 변경
- 프리릴리스: 실제 소비 앱 검증을 위한 베타 계약

지원 중단 예정 API에는 대체 API, 이전 지침, 최소 한 번의 마이너 버전 유예 기간이 필요합니다. `packages/react/api-baseline.json`과 생성 매니페스트 비교는 컴포넌트 prop, 기본값, ref 및 DOM 계약을 확인합니다. `packages/react/public-api-baseline.json`은 TypeScript 타입 체커가 읽은 패키지 진입점의 공개 값과 타입 export 전체를 비교합니다. 기준 갱신은 변경 영향과 SemVer를 사람이 검토한 뒤에만 수행합니다.

두 비교는 TypeScript 선언 계약을 다루며 CSS의 의미 변화나 모든 런타임 동작을 자동으로 증명하지 않습니다. CSS는 브라우저 시각 회귀로, 키보드와 ARIA 및 이벤트 동작은 상호작용 테스트로 보완합니다.

## 로컬 리허설과 실제 배포

Studio의 `Run rehearsal` 버튼은 실제 npm 배포가 아니라 로컬 릴리스 리허설을 실행합니다. 화면에는 같은 버전 계약을 공유하는 `@aster-ui/tokens`, `@aster-ui/react`, `@aster-ui/figma-bridge`를 대상 패키지로 명시합니다.

리허설 기록에는 스키마 버전, `local-rehearsal` 모드, 멱등성 키, 베타 채널, 실행 시각을 저장합니다. 검토자, Figma 소스 버전과 테마, 변경 지문, 품질 소스 리비전, 실행 ID, 산출물 해시도 함께 기록합니다.

현재 문맥과 정확히 일치하는 기록만 새로고침 뒤 복구하며, 화면 알림에는 외부 레지스트리를 변경하지 않았음을 명시합니다.

빌드에 삽입된 소스 리비전과 품질 근거의 리비전이 다르거나 다섯 품질 검증 항목이 모두 통과하지 않으면 확인란과 실행 버튼이 비활성화됩니다. 사용자는 `Quality` 화면에서 실패했거나 오래된 근거를 먼저 확인해야 합니다.

main 브랜치 CI는 `pnpm verify`로 품질 검사, 실제 브라우저 시각 및 접근성 검사, 프로덕션 의존성 감사, 근거 생성과 Studio 재빌드를 완료합니다. release-please 워크플로는 이 CI가 통과한 푸시에서만 실행하므로 같은 커밋을 중복 검증하지 않습니다.

의존성 감사 API의 네트워크 오류는 최대 세 번 재시도합니다. 모두 실패하면 잠금 파일이 동일하고 24시간 이내이며 실제 심각도별 건수가 기록된 성공 근거만 재사용합니다. 잠금 파일이 바뀌었거나 기록이 오래됐거나 high/critical 취약점이 발견되면 검증과 릴리스를 차단합니다. low/moderate 발견 건수도 보고서와 화면에 그대로 표시합니다.

릴리스 PR은 저장소 소유자가 Actions의 PR 생성 권한을 허용하고 `RELEASE_PLEASE_PR_ENABLED=true` 저장소 변수를 설정한 경우에만 SHA로 고정된 Action에서 생성됩니다. 이 저장소는 이 외부 쓰기 권한을 기본적으로 열지 않습니다.

Studio에 표시하는 근거는 최신 소스 변경 커밋과 결합한 로컬 검증 결과이며 GitHub Actions 성공을 대신하지 않습니다. 공개 CI와 Pages 배포 결과는 저장소의 Actions 이력에서 별도로 확인합니다.

## 소스와 검증 근거 커밋 순서

소스, 문서, 테스트와 시각 기준 이미지를 먼저 커밋한 뒤 `pnpm verify`를 실행합니다. 이어서 `reports/`와 `apps/studio/src/generated/quality-evidence.json`의 생성 결과를 별도 커밋합니다. 소스와 근거를 한 번에 커밋하면 근거에 기록된 소스 커밋이 직전 커밋을 가리킬 수 있습니다.

근거 전용 커밋은 소스 리비전 계산에서 제외됩니다. 마지막으로 `pnpm evidence:check`, `pnpm verification:check`와 깨끗한 작업 트리를 확인하고 두 커밋을 함께 푸시합니다. 이때 화면의 Commit은 근거 전용 HEAD가 아니라 최신 소스 변경 커밋을 가리키는 것이 정상입니다.

Studio의 Turbo 빌드 입력은 소스 리비전 계산에 쓰는 저장소 파일 전체를 포함합니다. 루트 문서나 검증 스크립트만 바뀌어도 번들에 삽입하는 리비전을 다시 계산합니다. 생성된 dist, coverage와 reports는 입력에서 제외하지만, 화면에 포함하는 quality-evidence.json은 별도 빌드 입력으로 유지합니다. 이 때문에 문서 변경도 Studio 캐시를 무효화하며, 과거 번들의 리비전을 재사용하지 않습니다.

Run ID는 CI에서는 GitHub 실행 ID이며, 로컬에서는 보고서를 생성한 프로세스의 `local:<pid>`입니다. 서로 다른 로컬 검사 보고서가 같은 Run ID를 가질 필요는 없습니다. 각 보고서의 출처와 해시를 검증한 뒤 통합 근거를 생성하며, 리허설 기록은 검토 문맥과 통합 근거의 소스 리비전, 소스 커밋, 해시에 결합됩니다.
